# TurfGPS requirements

The front door to the requirements corpus. Every functional and non-functional requirement lives in exactly one category file in this folder, in the canonical record form defined by `.claude/skills/requirements-authoring/SKILL.md`. This page holds the three things that change rarely and that everything else in the folder depends on: the **category register**, the **ID allocation ledger**, and the folder's **invariants**.

Why a folder rather than a file: `docs/README.md` § Requirements/.

**Corpus state — 4 August 2026.** 39 requirements, 10 categories in use. **18 are `to-build`; 21 are `draft`.** The twenty-one drafts are batch 3 — `FR-019` … `FR-034` and `NFR-001` … `NFR-005` — **awaiting the Owner's sign-off**; nineteen were filed on 3 August 2026 and `FR-033` … `FR-034` on 4 August, added to the same batch on a ruling that closed one of its own open questions. `draft` here means *filed and awaiting sign-off*, and nothing weaker: the records are in their category files, indexed, and carry a row each in `TRACEABILITY.md`. On sign-off they move from `draft` **straight to `to-build`**, as both earlier batches did, because `@requirements-reconciler` is dormant and there is no classification step for a record to wait in `approved` for — no record in this corpus has ever held `approved`.

**Batch 3 is the first batch to sit in `draft` after a filing pass**, and that is an ordinary state rather than a stall — it has simply never been observed here, because batches 1 and 2 were each signed off the day they were filed. `FR-001` … `FR-012` were signed off by the Owner on 1 August 2026 and `FR-013` … `FR-018` on 2 August 2026. Story creation has run for all eighteen of those: `@requirements-story-organizer` filed four epics and seventeen stories on 2 August 2026, in two passes, one per sign-off, and each of the eighteen is resolved by at least one story. The links live in `TRACEABILITY.md`; each record's `Resolved-by` and the column in `INDEX.md` are views of them.

**All twenty-one batch-3 records read `Resolved-by: —`.** The em-dash means *not yet allocated* — never *unknown*, and not an orphan: story creation follows sign-off as a pass of its own, and the orphan test applies to a requirement whose epic is in flight. Batch 3 has no epic yet, so it has not reached that test.

**Why the index is a separate file.** The allocation ledger is the only guard against ID reuse, and it must not sit below fifteen screens of index table where an author stops scrolling. The register and the ledger change rarely; the index changes on every filing. Keeping them apart means a routine filing does not rewrite the one file the whole RE family reads first, and two agents filing different categories do not serialize against a single file.

## Category register

The corpus's controlled `Category` vocabulary, and its only home. A `Category` value is legal if and only if it appears in the **Category** column below, copied verbatim. `@requirements-engineer` alone adds a name here — a new category is a decision, never a side effect of authoring. `@requirements-librarian` files each record under its `Category` and raises a record carrying a name not on this list as a finding, rather than filing it under a near-match.

**A name on this list is permission to file, not a promise that requirements exist.** Most rows read `reserved`: the source sections behind them have not been broken down yet. `reserved` means no file and no records, and nothing may be concluded from the absence — a category's absence from the *filed* set means unfiled, never illegal.

These names were consolidated on 1 August 2026 from coverage prompts that previously stood in four agent definitions, which named the same areas in four different phrasings and would have produced several files for one subsystem. Those lists remain in place as coverage prompts — questions an author asks per source section — and are explicitly no longer a source of category names.

**Extensions since.** `Value model`, added 1 August 2026 by `@requirements-engineer` while integrating `SPECIFICATION.md § The journey as an optimization problem`. The register as consolidated carried `Cost and time composition` with no counterpart on the value side, while the objective the whole product optimizes is value set against cost. Without it, everything the value half of that objective is built from — zone attributes, attribute rarity and preference, the rank-to-weight curve — would have filed under `Objective selection and ranking`, whose scope is how value and cost are *combined*, not what either is made of. Recorded here because a register extension is a decision, and a decision with no stated reason is indistinguishable later from a name someone coined in passing.

`Recommendation set composition`, added 2 August 2026 by `@requirements-engineer` while integrating `SPECIFICATION.md § Recommended journey alternatives`. The register carried `Route alternative generation` for producing corridors and `Objective selection and ranking` for the objective and the ordering under it, and nothing for the question that section actually answers: which of the alternatives produced are put in front of the user. Filing those records under `Objective selection and ranking` would have put set membership and set ordering in one file under a scope line that names only the second, and coverage per subsystem would have stopped being checkable for either. Recorded here because a register extension is a decision, and a decision with no stated reason is indistinguishable later from a name someone coined in passing.

`Turf data integration`, added 3 August 2026 by `@requirements-engineer` while integrating batch 3. The register as consolidated was seeded from the decision core and carried no category for the data plane at all — the layer between the Turf API and everything downstream of it. Batch 3 is the first batch to enter that layer. Filing these records under the decision-core categories would have put the integration contract in the same files as the optimizer's behaviour, and coverage per subsystem would have stopped being checkable for both. The boundary against `Call budget` is written into the scope line rather than left to be rediscovered, because the two abut and the line is not obvious.

`Zone data fidelity`, added 3 August 2026 by `@requirements-engineer` while integrating batch 3. Separated from `Turf data integration` deliberately. Its records bind the optimizer and the cost model rather than the integration layer, and folding them in would mean a reviewer asking whether the cost model assumes a minimum inter-zone distance has to read the integration file. It is small — three records — and the register already carries a category of one; size is not the test, subsystem is.

`Outbound rate compliance` and `Data currency and confidence`, added 3 August 2026 by `@requirements-engineer` on the Owner's ruling of the same day: `Turf data integration` splits by record kind, rather than the skill's one-kind-per-file rule bending to admit a category holding both. They are the NFR half of what batch 3 filed as a single `FR + NFR` category, and they close the open finding recorded under *How this folder works* below.

**The split is by subsystem too, not by kind alone, and that is why honest names exist for it.** A doubled register — one name per subsystem on the FR side and the same name with a word appended on the NFR side — would have made `Category` a restatement of `Kind` and would have said nothing about the system. It was avoidable because the two records were never held together by their subsystem in the first place: they were held together by their *source section*, and the FR file had already drawn the line between them in prose. `FR-024`'s `Rationale` reads *what the system may conclude from a copy of that age is a confidence question, and it is `NFR-002`'s* — the boundary between what the pipeline tolerates and what it may claim, written by an author with no idea it would become a filing boundary. The register now states that line instead of leaving it in one record's rationale.

**The NFR half of this register was never a subsystem vocabulary**, which is the deeper reason no doubling occurred. `Response time`, `Estimate accuracy`, `Call budget`, `Privacy`, `Portability`, `Observability` and `Maintainability` each name a **quality**, where every FR name names a **subsystem**. One column has carried two vocabularies since consolidation and `Kind` is what tells them apart — so `Turf data integration`, registered as `FR + NFR`, was the sole row spanning both, and the ruling's real effect is to remove the one exception rather than to introduce a division. Neither new name is a Turf-integration name with a qualifier: one names a compliance obligation at the egress edge and would hold a rate record for any limited upstream, the other names an age-to-confidence relation and would hold one for any ageing source.

`Runtime and deployment shape`, added 3 August 2026 by `@requirements-engineer` while integrating batch 3. Added to carry the NFRs that repository scaffolding satisfies, following the Owner's ruling of 3 August 2026 that `DELIVERY.md` carries **no traceability exception for scaffolding** and that scaffolding must be backed by real requirements. No existing category fitted: `Portability` is about adding a country as an adapter, `Maintainability` about the cost of the next safe change, and `Platform support` about the browsers the client must work in. What the build produces, and which deployment topologies the architecture rules out, had no home.

## ID allocation ledger

**Next free: FR-035 · NFR-006**

**Allocation is highest-ever-issued plus one, never lowest-unused**, so a retirement cannot free a number even if a tombstone is lost. One ascending sequence per prefix, the two counters running independently.

**`FR-000` and `NFR-000` are permanently reserved and are never allocated.** They carry the worked examples in `.claude/skills/requirements-authoring/SKILL.md`, which has to illustrate the record form without any illustration answering to a live requirement's identity. The reservation costs nothing: both sequences run upward from `001`, so neither number is reachable by the rule above. Until 3 August 2026 the skill's canonical example was numbered `FR-021`, which batch 3 then issued to a real record — `grep FR-021` returned one real requirement and one fictional one, and `FR-032`'s `Rationale` cites `FR-021` by number, so it resolved to either. **The example was renumbered and the record was not**, which is the only order the immutability rule permits: an allocated ID is immutable, and the example's number was never an allocation.

**The NFR sequence opened on 3 August 2026, with `NFR-001` … `NFR-005`.** Until batch 3 no NFR had ever been issued, and the emptiness was a recorded outcome rather than a gap: `@requirements-nfr` returned a considered zero for batch 1, scoped to `SPECIFICATION.md § Primary use case` and its subsection *The planning player* — neither states a quality attribute with an obligation attached — a second considered zero, argued and accepted, for `SPECIFICATION.md § The journey as an optimization problem`, the section behind `FR-007` … `FR-011`, and a third for `SPECIFICATION.md § Recommended journey alternatives`, the section behind `FR-013` … `FR-018`, argued at the foot of this ledger. **All three remain correct in their own scope and none is overturned by this batch.** They are still the reason `NFR-001` was free until now, and they are kept in full below for that reason.

The drought ended where those zeros did not reach. Batch 3's NFRs came from `Architecture.md § Data sources and constraints` and `Architecture.md § Technology decisions` — sections none of the three zeros covered, and neither of them a section a zero was ever put to. Nothing about the sequence opening here says a zero was wrong; it says a different document was swept.

**Batch 3's de-confliction, recorded so it is not re-litigated.** Four authored records did not file, and an ID was issued for none of them. The FR and NFR lanes swept the same Architecture sections in parallel, so the overlaps below are the ordinary product of that and not a fault in either lane.

- **A functional record on Turf rate limits was dropped in favour of `NFR-001`.** Both lanes authored the same obligation and both chose `test`. A bound on a rate is a quality, and `NFR-001` alone names the aggregation point — a limiter held per session or per worker satisfies a per-caller criterion and still breaches a limit the API applies to the system as a whole.
- **A non-functional record on solving against a refreshing or stale copy was dropped in favour of `FR-022` and `FR-024`.** It duplicated `FR-024` nearly word for word, and its one distinct clause — that a solve does not wait on the sync — is already `FR-022`'s second criterion.
- **A non-functional record forbidding an assumed minimum inter-zone distance was ruled functional** and re-authored as `FR-032`. A prohibition on a behaviour is not a quality attribute; an acceptance criterion of the form *count of X: zero* would make every prohibition an NFR. The content survived because `FR-021` genuinely does not reach logic that obtains no distance at all.
- **A fourth considered zero, on `Architecture.md § API version`, is accepted in its own lane** — the NFR lane returned it, and there is no quality attribute in that section. `FR-019` stands over it because it carries what neither Architecture section does: that **exactly one** API version is named, on error and fallback paths as well as primary ones.

**Amended after filing, 3 August 2026.** Recorded because a field changed after the batch was filed, and a diff alone would not say why. The first two follow the Owner's rulings of that day; the third is a conformance reject raised by the sweep those rulings forced.

- **`FR-025` drops from `SHOULD` to `COULD`.** `Architecture.md § Retrieving zones` makes the local synced copy the source for corridor resolution, while `Architecture.md § Volatile and optional fields` calls any locally cached copy a snapshot; the Owner ruled that the sync is the source and that no per-journey refresh is required for the first release, which puts the bounding-box endpoint — the only endpoint `FR-025` constrains — off the first-release critical path. The supporting measurement is `@data-architect`'s: **1.28% of zones change `totalTakeovers` per hour** and 23,119 of them, or 16.6%, per day, against a sync feeding data that is either near-static or rated over months. A per-journey refresh buys nothing measurable and adds a live API dependency inside every solve. **`COULD` and not `WON'T-now`**: the endpoint is not excluded — the same section keeps it as the fallback and as the means of refreshing volatile per-zone fields — so the obligation binds the moment that path is built and the statement stays `shall`. `WON'T-now` would file no story at all and leave a fallback free to construct requests the API rejects.
- **`NFR-001`'s second acceptance criterion now names the all-zones endpoint by role rather than by path.** It read `GET /v5/zones/all`, which made the record a second home for the API version — a constant whose home is `Architecture.md § API version`, and which `FR-019` exists to bind by citation, its `Rationale` saying exactly that. Raised by `@requirements-librarian` during the re-file sweep and rewritten by `@requirements-nfr`. **The reject is `Verifiable`, not merely `Conforming`**, which is why it was a rewrite and not a note: on a version bump the criterion would still have *passed*, vacuously, because a deployment on the next version issues no `/v5/` requests at all and the interval between zero requests satisfies any minimum. A criterion that reports green while measuring nothing is the one kind that can never fail. A `/v[0-9]/` sweep of the corpus returned that line and no other, and `FR-022` had already named the same endpoint version-free, so the record was the outlier against its own batch. Caught in `draft`: no story, no index row and no signed record moved with it.
- **Nothing is amended for `dateCreated`, and nothing needed to be.** Whether the live API still returns the field is being verified against the endpoint on the Owner's ruling of the same day; the January 2025 dump carries it, which establishes the dump rather than today. **No record in this corpus names `dateCreated`** — the field appears only in the upstream documents, under `CalculationSpecification.md § Takeover rate` and the sections citing it — so nothing filed rests on the answer and nothing was held back pending it. Recorded so that the batch which eventually reaches takeover rate finds the verification rather than re-deriving the question.

**Added to batch 3 after filing, 4 August 2026.** `FR-033` and `FR-034`, on the Owner's ruling of 3 August 2026 closing the batch's open third question: plan against whatever copy of the zone set exists and mark the result as built from stale data, refusing only where no copy exists at all. This is authoring rather than amendment — the obligation belongs to `Architecture.md § Retrieving zones`, a section batch 3 swept, and the batch is still `draft`, so no signed record moved and no story was disturbed. **The ruling produced two records rather than the one commissioned**, and the split is recorded here because a one-record commission returning two reads as drift unless the reason is written down. Planning past the bound and recording what the plan was built from are two separately testable outcomes on the **same** branch, so a statement joining them would be half-satisfiable by the half that keeps the product working — which is the half nobody forgets to build. Planning and refusing, by contrast, are two branches of one gate reading one input, whether a copy is held, and they stay together in `FR-033` exactly as `FR-012`'s three criteria do. Both are `MUST`: the ruling permits degradation **on condition** that it is disclosed, and a split made for singularity must not quietly demote the condition below the behaviour it conditions.

**No register extension was needed for either, and one was considered.** `FR-034`'s subject is the result rather than the data plane, which argued for a category of its own; it was rejected. `Data currency and confidence` is registered `NFR` and cannot hold a functional record. A new functional category for one record would put the marking rule in a different file from the planning rule it conditions, so a reviewer asking what happens past the bound would read two files for one ruling, and it would pre-empt `Persistence and staleness`, which owns whether that fact survives storage and retrieval. The deciding line is one the register has already drawn: `FR-024`'s rationale puts what the system may **conclude** from a copy of that age on the confidence side, with `NFR-002`. `FR-034` concludes nothing — it records a fact about provenance — so it sits on the pipeline side of a line already drawn, and needs no new name.

**What no zero covered, recorded so the emptiness above is not over-read.** `SPECIFICATION.md § Genuinely out of reach or out of scope` is cited by `FR-005` and is `FR-012`'s sole source, but it entered batch 1 only as a corroborating second citation and was never swept as a section: five of its six bullets carry no requirement at all, and `FR-012` arrived from an Owner ruling rather than from a batch scoped to it. No NFR question has been put to it, and the absence of one there is **unexamined rather than a considered zero of its own**. That section is owed a batch of its own — an earlier wording of this paragraph described batch 1 as covering "the two source sections behind `FR-001` … `FR-006`", which counted a citation as a sweep and is corrected here.

Owed for the same reason, and noticed while `FR-012` was authored: *The planning player* states that the tool is used in a planning session rather than while driving, "which relaxes how quickly the first answer must appear". A relaxed target is still a target — but the obligation's home is `Architecture.md § Response time and progressive results`, not the section observing it, which is the same reasoning that produced the second zero below. **A `Response time` NFR is owed when a batch scoped to that Architecture section runs**, and is deliberately not allocated here.

**`SPECIFICATION.md § User time constraints` is owed a batch of its own, and this debt is not merely an unswept section.** Batch 2 actively deferred obligations to it: `FR-013`, `FR-017` and `FR-018` each disclaim in their `Rationale` an obligation that section owns — that there must always be at least one journey alternative within the user's stated additional-time limit — naming it as the single definition of the allowance rather than restating it. The consequence has to be written down plainly, because it cannot be seen from the records themselves: **until that batch runs, no record in the corpus obliges the offered set to be non-empty**, and every batch-2 record is vacuously satisfiable by a system that offers nothing at all. Owed to the same batch and deferred for the same reason: the allowance itself, the absolute ceiling over it, the value-based justification a stretch alternative requires, and a stretch alternative's identification as one.

**A second hole of the same shape, and it is not the one above.** Found by `@requirements-story-organizer` while cutting batch 2's stories, and recorded here because it cannot be seen from any record on its own. The debt above is that the offered set may be **empty**; this one is that it may be **singular**. Every batch-2 criterion is conditioned on alternatives *having been produced* — `FR-013`'s first criterion opens *given a journey for which more than one alternative … has been produced* — and **nothing anywhere in the corpus obliges the system to produce more than one alternative in the first place**. A search that only ever yields one satisfies `FR-013` without ever putting a choice in front of a user, which is the whole of what that record exists to secure.

The obligation's home is `Route alternative generation`, which is `reserved` on the register above: no file, no records, and the section behind it unswept. **It is owed to the batch scoped there**, and it is deliberately not authored now — writing it here would be admitting scope through the side door that story creation opened, and the register entry exists precisely so it is not. Recorded rather than storied, and carried on `#12` as an openly-stated hole so no worker reads that story as guaranteeing a plural result.

**Owed by batch 3, and deliberately not authored.** Four debts, each with a stated home, so none of them is later mistaken for an oversight.

**The honesty residue of confidence against data age.** A `human-judgement` record was authored — that a recommendation built from ageing Turf data must not present a confidence overstating how current it is — and is **held unfiled pending an Owner ruling**, not rejected. `SPECIFICATION.md § Confidence and uncertainty` enumerates ten uncertainty drivers and every one is a source of error in the *travel-time estimate*; data age is not among them, and stale ownership does not make a time estimate wrong, it makes a *value* estimate wrong. So the open question is not whether that enumeration is incomplete but whether it is the right standard at all. `NFR-002` carries the machine-checkable relation; the residue is owed to the batch scoped to `SPECIFICATION.md § Confidence and uncertainty`.

**Owed to the `Call budget` batch** — `Architecture.md § The call budget`, batch 4: the per-journey Turf call bound; the one-call properties of held-zone and region-lord retrieval; and the over-tiling concern in *Retrieving zones* — splitting a corridor into tiles far below the permitted area — which is a call-volume claim with no threshold that was not invented.

**Owed to failure handling, which `Architecture.md § Still owed by this document` has not written:** what the local copy is, and what may be concluded from it, when a sync fails or completes partially. `Architecture.md § Retrieving zones` records a five-minute timeout as an observed fact and states no obligation about the result.

**`SPECIFICATION.md § Non-functional requirements` is an entire unswept section**, holding *Platform and mobile-first design*, *Geographic scope*, *Languages*, *Estimate accuracy and calibration* and *Time of day and traffic*. It is the corpus's largest unworked NFR source and it is owed a batch of its own.

**Why the second zero, recorded so it is not re-litigated.** That section names the one-home-per-model invariant while complying with it — the scoring model is defined once, in `CalculationSpecification.md`, and not restated. The obligation is created by `docs/README.md` § Conventions, not by the section observing it, so an NFR sourced from the observation would cite the wrong home; and narrowing it to the scoring model alone would shard a corpus-wide invariant per occurrence, giving the one-home rule more than one home — the exact defect it exists to prevent. **One corpus-wide `Maintainability` NFR, verified by `inspection`, is owed when a batch scoped to `docs/README.md § Conventions` runs.** It is deliberately not allocated here.

**Third considered zero — `SPECIFICATION.md § Recommended journey alternatives`, 2 August 2026.** The section states one obligation of its own — curate the offered set, avoiding effective duplicates and alternatives with no meaningful trade-off — and everything quality-*sounding* in it is the standard by which that one duty is judged, not a second duty. "Meaningfully different", "effectively duplicates" and "meaningful trade-off" are the adverbs of the curation rule; the corpus's home for a standard of judgement is the `Verification` field of the record carrying the duty, never a companion record. An NFR restating them would be the same sentence filed twice, split only by verification method, and would collide head-on with the FR sweep of this same section. One obligation, one home.

No threshold exists to hang a metric on. "Several" is not a count, and nothing in `CalculationSpecification.md`, `Architecture.md` or `DESIGN.md` sets a number of alternatives to present or a distinctness bar between them. The fallback is not `Coverage and data quality`, and this is the trap the section sets. That category degrades on **thin map or elevation data**, with confidence falling as it thins. ## How this folder works

- **IDs are immutable.** Never reused, never renumbered, never recycled after deletion. Whoever issues the next one takes it from the ledger above and nowhere else.
- **`INDEX.md` carries a row for every ID ever issued**, including retired ones. A retired requirement keeps its record, in place and in ID order, reading `Status: retired`; it is never deleted and never moved. There are no tombstones today because no ID has ever been retired — `FR-001` … `FR-034` and `NFR-001` … `NFR-005` are each contiguous with no gaps.
- **A retired record's `Resolved-by` freezes at its last value.** Retirement removes the requirement from the *Requirement → story* table in `TRACEABILITY.md`, so the link's single home disappears with it — but the field on the record and the column in `INDEX.md` keep whatever they last read rather than reverting to `—`. They are then the only surviving record of what was built for that requirement, and blanking them would erase it. A frozen value is not stale and is not a finding.
- **Records sit in ID ascending order inside their file, and that order never changes** — not on retirement, not on re-prioritization. A file's order is therefore a fact about IDs alone, and a diff never moves a record it did not touch.
- **The record is authoritative; every index is derived.** Where a row in `INDEX.md` and the record in a category file disagree, the record is right and the row is stale — a librarian finding, fixed in the index, never fixed by editing the record to match.
- **Records are filed verbatim inside fenced blocks**, preserving the field alignment of the canonical record in `requirements-authoring`. The librarian moves, groups, indexes and cross-links records; it never re-words one. Content questions go to `@requirements-engineer`.
- **Category files are named as the kebab-cased `Category` field**, verbatim and unnumbered, so a record names its file and a file names its category with nothing to look up, and adding a category never renames one.
- **A `Category` never spans both kinds, and the `Kind` column holds one value.** Raised as a finding on 3 August 2026 by `@requirements-librarian` and ruled the same day. `Turf data integration` had been registered `FR + NFR`, producing a file that held ten FRs and then `NFR-001` … `NFR-002`, and `.claude/skills/requirements-authoring/SKILL.md` § Corpus layout cannot be satisfied whole by such a category: it states in one breath that a file is named as its `Category` verbatim and that **FRs and NFRs share the folder, never a file**. The batch filed under the naming rule — the one traceability rests on, since a record names its file with nothing to look up — and marked the file explicitly non-precedent, which is why the ruling cost a re-file rather than a migration. `@requirements-engineer` proposed amending the skill so that one category may hold both kinds; **the Owner kept the skill as written and split the category**, on the ground that a file's kind then stays trivially checkable and the librarian's conformance sweep stays mechanical. `NFR-001` and `NFR-002` moved to `Outbound rate compliance` and `Data currency and confidence`, registered above with their reasoning.
