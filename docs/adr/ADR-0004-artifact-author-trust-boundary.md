Put together, these are not six observations but one mechanism. A validation result is a comment whose body opens with `artifact: validation_result`; a consumer finds it by that string and reads what follows. **Any account on GitHub can write that string.** `@linus-security-critic` demonstrated it against PR #187: a comment declaring `status: pass` with the live head SHA is read as a pass for gates that nobody ran, by a consumer that has no field left in its hands with which to doubt it. The projection is what closes off the doubt — a consumer that wanted to check provenance could not, because the published command threw the author away before the consumer saw it.

The judge lane shows the shape of the answer, having already needed it. It does not extend to this one: it is a rule about a *verdict's* signature, and a validation result is deliberately not a verdict.

## Decision — the Owner's

`§ D1` through `§ D3` are the Owner's decision set and nothing else is in it. An engineering decision taken alongside them is recorded separately, under `§ Engineering decisions recorded beside the Owner's`, with its own author and its own reasoning.

### D1 — The allowlist is two names, and for them nothing changes

Artifact authorship is trusted for exactly **`Caisesiume`** and **`TheReviewNinja`**. An artifact authored by either is read exactly as it is read today: the declared class selects it, the body is consumed, and no new step is added on the path that carries all of this repository's real traffic.

This is the Owner's "it should remain the same way as today," and it is a deliberate choice of the cheapest possible hardening. The reader gains a comparison against a two-element list. It gains no policy engine, no signature scheme, and no new artifact class — every one of which would be a larger change to the mechanism than the vector justifies.

The list is closed. Adding a third name is an Owner decision and an amendment to this record, not a judgement any agent makes at read time.

**The allowlist is a floor, not a ceiling, and it is class-blind.** It says which authors may be read *at all*; it never says that every artifact class must accept both of them. A stricter rule on a particular class survives this decision untouched — specifically the judgment-author rule in `turfgps-board-ops § The one thing the fallback must never do`, already noted in `§ Context` above, under which `artifact: judgment` still refuses every author but one even though `§ D1` admits two. Read the two together as floor and ceiling and nothing is lost; read `§ D1` as a ceiling and the judge lane's existing boundary is silently widened by a record that claims to narrow. `@linus-security-critic` and `@linus-architecture-critic` filed this jointly as `TRUST-01` on PR #188.

### D2 — An unlisted author declaring an artifact is escalated to the Owner as a question, and is never discarded

An artifact whose author is not on the list is **neither trusted nor dropped**. The agent stops consuming it and puts it to the Owner **in question form**, for the Owner to judge — in the Owner's own terms — "it's readiness and correctness."

**The trigger is narrow. The narrowing is the Owner's decision; the sentences stating it are `@engineering-lead`'s proposal**, and `§ The decisions as given` quotes each with its author rather than presenting the proposal as the Owner's wording. Escalation fires **only when a non-allowlisted author posts something declaring an `artifact:` key** — something attempting to be read as an artifact. **An ordinary human comment from a contributor is not escalated**; it is a comment, and nothing in this record turns comments on a public repository into interrupts. **Untrusted text is to be quoted to the Owner as inert data and never relayed as instructions** — written here as what the escalation must do, not as something the machinery already does.

**Each half of that closes a hole the first version of this decision opened, and both were real.** Escalating on *any* comment from an unlisted account made the trigger unauthenticated, free, and rate-unbounded: any account on GitHub could page the Owner repeatedly, on every open pull request, at no cost and with no way for the Owner to make it stop short of locking the repository — a denial-of-attention channel handed to strangers by a record whose purpose was to reduce exposure. And relaying the text as something to act on turned the escalation into a **delivery channel for the `#152` injection class this record cites as its own justification**, aimed at the one reader with the most authority. Quoting as inert data is what keeps the never-discard promise without carrying an instruction into the Owner's context. **That control does not exist yet, and this record does not get to write it.** An escalation packet is the only shape in which anything reaches the Owner and `@engineering-lead` is its only sender, so the control's home is `handoff-payloads § Escalation packet` — where, checked on 2026-09-17, no field carries quoted untrusted text and nothing requires it to be inert. The control is therefore **owed and not in force**, and `§ Consequences` lists it with the rest of what this decision obliges elsewhere. `@linus-security-critic` filed the present-tense claim as `SEC-07` on PR #188.

**Discarding it would be wrong, and this record says so plainly rather than leaving it to be inferred.** An artifact-shaped comment from an account outside the list is not by construction an attack. It may be a legitimate contribution: a reader who reproduced a failure, a passer-by who spotted a real defect, a future collaborator. Silently dropping it makes the repository unable to receive that, and does so invisibly — nobody is told, so nobody can notice the policy is costing something. The one party entitled to decide whether such input is sound is the Owner, and the escalation exists to put it there rather than to have an agent guess in either direction.

Both failure directions are therefore refused. Consuming an unknown author's artifact treats a stranger's claim as a measurement; discarding it silently treats a contribution as noise. The escalation is the only path that resolves neither way on its own.

**The escalation fires only where something already looked, and that residue is named here rather than closed.** The trigger is a predicate on a comment, and it is evaluated only by a consumer that retrieved that comment — which retrieves under its own **selection** predicate, narrower than the escalating one: the selector in `§ Context` matches `artifact: validation_result` alone, while `§ D2` fires on any declared `artifact:` key. **This record does not require the escalating predicate to be a superset of the selecting one.** An artifact-shaped comment whose declared class no consumer pages for, or which sits where nothing is currently consuming, is never retrieved and therefore never escalated. Mandating the superset would widen what the Owner decided and put a standing cost on every retrieval, so it is **named as a residual and left to an Owner decision**, exactly as `.user.id` and `.updated_at` are elsewhere in this record. What `§ D2` promises is that an artifact-shaped comment a consumer *reads* is neither consumed nor dropped; it does not promise that every such comment is seen. `@linus-security-critic` filed this as `SEC-10` on PR #188.

**This is a §21 escalation and it carries a recommendation.** `ADR-0001 § D6` makes §21 the only human-escalation policy here and blocks on §21-qualifying questions alone. The Owner has ruled this trigger a **sixth** §21 category rather than an exception to that rule, and has required it — like every other §21 rung — to reach the Owner with a **proposed answer**, on the standing rule that a question without a recommendation is work handed back. The agent therefore states what it would do with the artifact and why; "what should I do with this?" is not an escalation. The amendment is `ADR-0001 § D16`.

**Nothing waits synchronously, because nothing in this organization can.** The consumer does not block in place until the Owner replies — there is no mechanism for that. **`ADR-0001 § D11` governs how such a pass ends, and it points the other way from the way this sentence once cited it:** D11 forbids *ending* a pass while a continuation is outstanding unless the agent either awaits it or **persists it to a durable artifact and names what remains owed and to whom**. The consumer here takes the second branch, which is what makes ending the pass lawful rather than the defect. `@linus-architecture-critic` filed the inverted citation as `LA-07` on PR #188. The flow is the one every human-bound question already uses: the consumer returns `status: blocked` per `handoff-payloads § Structured uncertainty (blocked)` and **ends its pass**; `@engineering-lead` owns the channel to the Owner and shapes the question per `handoff-payloads § Escalation packet`; the item is labelled `awaiting-human` and parked, which is what `turfgps-board-ops § Labels` means by a paused loop. This record adds a trigger to that machinery and does not add a second channel beside it. `@linus-architecture-critic` filed the synchronous-wait error as `LA-02` on PR #188.

### D3 — The selector retains `.user.login` and `.created_at`

The Owner called this out specifically — the Owner's words, with the Owner's punctuation and no formatting added inside them: ".user.login and created at are still needed and a great approach in addition." Any retrieval that a consumer is instructed to run **carries the author and the creation timestamp through to the consumer**. A projection that discards them is a defect, because it removes from the reader the only fields on which `§ D1` and `§ D2` can be decided at all — an allowlist is unenforceable against a body that arrived alone.

`.created_at` earns its place twice. The second use is the ordering gap `@linus-security-critic` filed as `SEC-04` on PR #187: when several results exist at one head SHA, a consumer needs a rule for which one is the result, and a timestamp makes that tie-break computable instead of leaving it to whichever comment the page happened to return first.

**What is normative here is that the two fields the Owner named — `.user.login` and `.created_at` — survive projection**, not any particular command. Two, not three: `.id` also fails to survive the projection described in `§ Context`, and the Owner did not ask for it, so this record does not require it. The command's one home is the agent definition that publishes it, and this record deliberately does not become a second one — `local-gates § Documentation gates` gate 2 is the reason, and the selector fragments described in `§ Context` above are dated evidence of a shape observed on a specific day, not a copy of the instruction.

**These two fields prove creation. They do not prove integrity, and reading them as though they did is the next mistake available.** A comment body stays editable and deletable by its author for as long as the comment exists, and `.created_at` does not move when the body changes — so a comment that was benign when a consumer first saw it can be rewritten afterwards while both retained fields read exactly as before, and a comment that has been deleted reads as never having been posted at all. **`.updated_at` is the field that would show the edit, and requiring it is a widening of what the Owner decided**, so it is named here as available rather than mandated. What `§ D1` and `§ D2` get from the two retained fields is the ability to decide *whether to read at all*; what they do not get is any assurance that what was read is what is there now. `@linus-security-critic` filed this as `SEC-04` on PR #188 — a different finding from the PR #187 `SEC-04` above, per `§ Context`.

## Engineering decisions recorded beside the Owner's

An engineering decision recorded beside an Owner decision is useful; one recorded *inside* an Owner's decision set is a misattribution, and misattribution in a decision record is the failure mode the record exists to prevent.

Both acts, and the absence of any Owner instruction on the point, are recorded at PR #188 `#issuecomment-5713681420`. `@docs-reviewer` filed the misattribution as `DOC-07` on PR #188. The Owner's set is `§ D1` through `§ D3`. The principle itself was not wrong, only misattributed, so it is restated below as `§ E1` with its real author; **the identifier `D4` is retired and is not reused**, so that a reader meeting an older citation naming a `D4` on this record knows it points at a decision that was withdrawn rather than at some later fourth decision. That citation resolves to nothing here, deliberately.

### E1 — No artifact is a clearance

*Decided by `@engineering-lead`, on a recommendation from `@linus-security-critic`. Not an Owner decision.*

An artifact reporting `pass` is **evidence that a measurement was taken**. It is an input to `@pr-judge`'s ruling and never a substitute for it. This holds for artifacts from allowlisted authors too — `§ D1` admits an artifact to being *read*, and admits it to nothing else.

This is the same principle `docs/DELIVERY.md § Escalation and human judgement` already states for the board: "a clean board is a **recommendation to the human**, not an approval." It is restated as a decision rather than left as a citation because the allowlist creates the temptation it guards against: a trusted author makes a `pass` feel dispositive precisely when the mechanism has just been described as hardened. It has not been. It has been narrowed.

**This binds cooperating consumers and nothing else, which is the limit of what a rule in a document can do.** It is an in-band instruction to agents that read it and choose to obey it. An adversary holding a trusted account is not such an agent: it can post a `pass`, and `§ E1` does not stop the artifact being posted, read, or believed — it only tells a well-behaved consumer not to treat the reading as an approval. **The backstop against that case is not `§ E1` and is not any part of this record; it is human review**, the Owner or a human reviewer looking at the change before it merges, which is exactly what `docs/DELIVERY.md § Escalation and human judgement` reserves to a person. Anything else stated here would be a control this repository does not have. `@linus-security-critic` filed this as `SEC-06` on PR #188.

## Consequences

**What this obliges:**

- **Every consumer that retrieves a declared artifact *carrying an author field* acquires a branch it did not have.** Read, escalate, or stop — decided per artifact, on the author. The qualifier is load-bearing: the branch is decidable only where an author exists to compare, so it reaches retrievals of posted comments and **does not** reach an artifact handed over in-process or read from a file, which carries no author at all. `scripts/gates/output-caps.sh` is the standing example — it classifies an artifact by its declared `artifact:` key and is out of scope here, because nothing it reads has a `.user.login` to test. The cost, where the branch does apply, is one comparison against a two-element list on the path that carries essentially all traffic, and this is the cheapest form the decision could take. `@linus-architecture-critic` filed the over-reach as `LA-04` on PR #188.
- **Five files must change: one changes here, two are PR #187's, and two are owed.** The count has been wrong twice by undercounting, so it is written as a list rather than as a number.
  - `docs/adr/ADR-0001-artifact-driven-agent-org.md` — **changes in this diff**, as `ADR-0001 § D16`, because the `LA-01` ruling is what makes `§ D2` lawful.
  - `@validation-agent` and `agent-handoffs` — the reader hardening, **exactly the diff PR #187 has open and under judgment**, and neither is touched from this branch: a second writer in a file already being judged is the hazard the one-writer rule exists to prevent, and a decision record that quietly implements itself is not a decision record. That implementation cites this ADR when it lands. The earlier count of two omitted ADR-0001 and was filed as `LA-04` on PR #188.
  - `docs/DELIVERY.md § Escalation and human judgement` and `handoff-payloads § Escalation packet` — **owed, and recording the obligation is the only thing this branch may do about it.** `ADR-0001 § D16` declares a sixth blocking escalation category; checked on 2026-09-17, those two still enumerate **five** conditions and close the enumeration with "nothing else qualifies". `@engineering-lead` is the **sole sender** of an escalation packet and takes its qualifying conditions from exactly that pair, so **until they carry the sixth category, the one agent able to raise this escalation reads a closed list that excludes it and drops the artifact silently** — the discarding direction `§ D2` refuses outright, reached through a document rather than a decision, with nothing anywhere reporting that it happened. **`§ D2` and `ADR-0001 § D16` therefore bind nowhere else yet:** the category is in force only once that propagation lands, and this record claims no more than that. Neither file is edited from this branch, for the one-writer reason above. `@pr-judge` filed this as `CORE-01` on PR #188, on findings `@linus-security-critic` and `@linus-architecture-critic` raised as `SEC-08` and `LA-05`. `handoff-payloads § Escalation packet` owes the inert-data control of `§ D2` as well, filed as `SEC-07`.
- **A new stall is possible, and its trigger is now bounded.** An artifact-shaped comment from an unlisted author parks its consumer's item on the Owner. Under the Owner's narrowing in `§ D2` the trigger fires **only** on a comment declaring an `artifact:` key. **What that removes is the accidental pager, not the deliberate one, and calling it a bound on cost overstates it.** An ordinary comment now costs nobody anything, so a stranger commenting in good faith no longer pages the Owner by accident. To anyone willing to type the key, the trigger remains **free and unlimited** exactly as before — unauthenticated, unrated and unpriced — and the narrowing moves the price of paging the Owner deliberately from nothing to nothing. `@linus-security-critic` filed the overstatement as `SEC-09` on PR #188. What remains is that the trigger is still **unauthenticated**: anyone may post such a comment, and the stall is **per artifact**, not per author and not per repository, so N artifact-shaped comments park N items. Each one is an `awaiting-human` label rather than a held pass, so the loop continues on everything else while they wait. `@linus-security-critic` and `@linus-architecture-critic` filed the unbounded original as `STALL-01` on PR #188; the Owner's narrowing is what answers it, and the residue is recorded rather than glossed.
- **The list is a maintenance surface.** Two names are written into the repository's trust model. A new collaborator or a second review identity is now a change to this record. *Account rename and deletion are not maintenance and are listed below as residual vectors, which is the honest place for them.*

**What this gives up:**

- **Authorship on GitHub is not authentication.** An allowlist tests a login, and a login is not a signature. It is what is available without a key-management scheme this project does not have and does not need. It stops the **anonymous** stranger, which is the vector actually demonstrated — and that is the whole of what it stops, not the whole of the stranger problem.
- **A login string is re-registrable, and the allowlist tests the string.** GitHub frees a login when an account is renamed or deleted, and another account may then take it. An allowlist holding `Caisesiume` and `TheReviewNinja` as text would admit whoever next holds either name, silently and with no artifact changing. Renaming and deletion are therefore residual vectors and not a maintenance chore. **The fix is not in this record**: `.user.id` is a stable numeric identity that a login is not, the Owner did not ask for it, and adding it here would widen what the Owner decided — so it is named as the available answer and left to an Owner decision. `@linus-security-critic` filed this as `SEC-05` on PR #188.
- **It does not close the collapse `SEC-02` recorded on PR #187, and pretending otherwise would be the worse outcome.** The default CLI is authenticated as `Caisesiume` — the same account that authors the branches under review. `turfgps-board-ops § The one thing the fallback must never do` names that in its own words for the judgment case: a judgment posted through the plain CLI "would appear as `Caisesiume` — the author approving their own work ... and it would look completely normal in the history." An allowlist admitting `Caisesiume` therefore cannot tell a worker's artifact from the branch author's own tooling, because at the transport layer they are the same account. **This decision closes the anonymous-stranger vector only once the reader hardening lands.** As of 2026-09-17 nothing on any branch compares an author against the list — that implementation is PR #187's and is listed as owed in the obligations above — so in the running system the vector is **still open**, and this record is a decision about it rather than a control over it. A present-tense "is closed" against an unlanded hardening is what `@linus-security-critic` filed as `SEC-11` on PR #188. **The self-authorship vector is not closed by this decision at all**, and no widening of this list can close it — a list that admits an identity admits everything wearing it. What answers that one is `§ E1`: the artifact is not the clearance, so an artifact that authenticates as the author still buys nothing but a reading — and `§ E1` in turn binds only a cooperating consumer, so the real backstop there is human review.
- **Nothing is gained against a compromised trusted account**, and the same `§ E1` argument, with the same limit, is the only thing standing behind that case too.
- **`§ D2` carries untrusted text toward the Owner, and that is a cost this record must own rather than describe as a benefit.** The escalation moves a stranger's words into the context of the person with the most authority over this repository — which is the `#152` prompt-injection class this record cites as its own justification, pointed at the highest-value reader in the project. The Owner's narrowing bounds it on one axis and **owes** the other: the trigger fires only on an artifact-shaped comment, and the text is **to be quoted as inert data, never relayed as instructions** — a control `§ D2` states and `handoff-payloads § Escalation packet` does not yet carry, so it is owed rather than in force, per the obligations above. Once it lands it reduces the exposure; even then it does not remove it, because a human reading quoted hostile text is still reading it. The alternative — discarding silently — was refused for the reasons in `§ D2`, so the residue is accepted knowingly and is written here so that nobody has to rediscover it. `@linus-security-critic` filed this as `SEC-01` on PR #188.

**Reversibility: high.** The decision is a comparison and two retained fields. Removing the comparison restores today's behaviour exactly; the retained fields are additive and harm nothing if never read. No data migrates and no artifact already posted becomes invalid. **The `ADR-0001 § D16` amendment is the one part that is not purely additive** — it adds a §21 category, and reversing this record means withdrawing that category too, which is an Owner decision rather than a revert.
